# 扩展方案：Bark 通知 → 快捷指令 → iPhone 闹钟

核查日期：2026-10-13。适用模块版本：`0.1.1`。

**本文是可按步骤搭建的设计文档，不是已经安装到手机的成品。** 本次扩展只增加文档，不改模块源码、服务器配置或手机自动化；未提供或伪造可导入的 iCloud 快捷指令分享链接。

## 1. 先看结论

推荐链路：

```text
获授权的日历变更
  → 云端写入 iCloud 日历并回读成功
  → bark_send 发固定低敏标记 CALSYNC-NOTICE
  → iPhone 收到 Bark 通知
  → iOS 27 的“通知”自动化匹配 Bark + 标记
  → 运行本机固定快捷指令“同步日历闹钟”
  → 读取指定 iCloud 日历中的 [闹钟] 事件
  → 按事件时间，在本机“时钟”创建/同步普通闹钟
```

Bark 只负责提醒手机重新检查日历。闹钟的时间和范围由手机内预先配置的规则与指定日历决定，不把推送正文当作命令执行。这样延迟或重复通知不会重新执行某个旧的“设成 09:00”指令。

### 1.1 到底是触发读日程，还是识别消息来设闹钟？

**第一版采用“固定标题匹配触发 → 读指定日历 → 按明确字段建闹钟”。** 两处匹配用途不同：

- 通知标题 `CALSYNC-NOTICE`：决定**什么时候运行**同步快捷指令。
- 日历标题前缀 `[闹钟]`：决定**哪些日程纳入**闹钟清单。

真正的响铃时间来自日历的**开始日期/时间**，再减去快捷指令中预先设置的提前分钟。不是从消息汇总里搜索“明早”“提醒我”“九点”等词后猜时间。

| 接法 | 收到通知后做什么 | 优点与限制 | 本方案选择 |
|---|---|---|---|
| 固定标记触发，再读日历 | 只匹配 Bark 与固定标题；重读指定日历，按开始日期计算 | 时间来源明确；要处理手机日历同步延迟 | 第一版推荐 |
| 解析固定格式消息 | 读取消息里的 ID、绝对时间、时区、版本、失效时间 | 可减少对日历同步的依赖；须先证实通知输入可读，并实现鉴权、去重、过期和取消协议 | 后续单独开发，不是现有能力 |
| 汇总消息/自然语言识别 | 从一段摘要里识别关键词、推断日期和事件 | 易受否定句、改期、旧消息、多个时间和摘要改写影响；不能只靠关键词保证正确 | 不用于第一版无人值守建闹钟 |

例如“明天九点的会议取消，改后天十点”包含两个时间和一次取消，仅匹配“会议/九点”会设错。若用户只在聊天中交代日程，应先在获授权的日历流程里确认并写成明确事件，再发送同步信号；**Bark 消息不替代日历数据，也不额外授权日历写入。**

Apple 官方文档证明的是“可按通知字段过滤以触发”，并未在该页承诺可取得完整历史消息、系统通知摘要，或向下一动作交付可任意解析的通知对象。因此不用“汇总所有通知后识别关键词”的隐含前提搭建本版。[Apple 通知触发条件](https://support.apple.com/guide/shortcuts/event-triggers-apd932ff833f/10.0/ios/27)

### 1.2 最小接线清单：手机上具体放哪些动作

这是第 3–6 节的短版；先搭预览并验收，再启用真实 Clock 修改。

**A. 外层自动化只负责启动：**

1. 先建固定快捷指令“同步日历闹钟”。若该机支持把自动化附在快捷指令内，路径为：打开该快捷指令 → 编辑 → 自动化 → 通知；若是独立自动化界面，走“自动化 → 新建个人自动化 → 通知”。以本机实际入口为准。
2. App 选 **Bark**；过滤字段选 **标题 / Title**，值为 `CALSYNC-NOTICE`。界面支持等于时用等于；只有包含时用完整专用标记。无需根据正文拆词，也不匹配 `group`。
3. 自动化运行这个固定快捷指令。若设备仍用独立自动化编辑器，就只添加“运行快捷指令 → 同步日历闹钟”。不把通知输入传成脚本名、URL 或闹钟时间。
4. 只有界面支持时才选“立即运行”；首次权限、Bark 可选性、锁屏行为按第 5 节测试。没有“通知”入口时直接走第 7 节的手动/定时入口，同一个内部快捷指令不用重写。

**B. 内层快捷指令负责选日程与创建：**

1. “数字”固定为 `15` → “设定变量”命名 `LeadMinutes`；要事件开始时响，就手动把它改为 `0`。第一版不根据每条消息变化。
2. “当前日期”存 `Now` → “调整日期”加 `23` 小时存 `WindowEnd` → 再加 `LeadMinutes` 分钟存 `QueryEnd`。
3. “查找日历日程”：固定指定日历；开始日期在 `Now` 到 `QueryEnd`；按开始日期升序；关闭数量限制。随后只保留标题以 `[闹钟]` 开头、非全天且未被拒绝的事件；本机无法判定的邀请先不纳入。
4. “重复每一项”：取**开始日期**减 `LeadMinutes` → 得到 `Target`；秒归零。仅将未来且早于 `WindowEnd` 的目标加入清单；新增/重新打开前还要有至少 `60` 秒余量，已临近的正确启用项保持不动。
5. “格式化日期”得到完整 `yyyy-MM-dd HH:mm` → 加专用前缀 `CALSYNC|v1|` → 按完整标签合并同分钟目标。
6. 预览模式下只“显示结果”。启用写入后，“查找闹钟”：无匹配才“创建闹钟”；唯一匹配先核验时间/非重复属性，再明确“打开”；多个匹配只报告，不相互关闭。
7. 末尾只读复查并“显示通知”。改期、取消留下的旧受管闹钟，基础版列出待核对项，由用户确认后人工关闭；不是已实现的自动撤销。

完整的余量边界、读取失败、重复和旧标签处理以第 4 节为准。Bark 与日历独立同步；可短等约 5 秒、必要时再等约 15 秒重查，但相同结果不证明云端最新版已到手机。不要把这份动作清单当作已安装、已锁屏通过的功能。

### 1.3 字段从哪里来，哪些完全不读

下面是设计中的变量名，并非新增 MCP 参数或 Apple 保证提供的 API 字段名：

| 字段/变量 | 唯一来源与定义 | 第一版处理 |
|---|---|---|
| 通知 App | 自动化手工选定 Bark | 只作触发来源过滤 |
| 通知 `title` | `bark_send.title` 固定 `CALSYNC-NOTICE` | 只作唤醒标记，不含日期或命令 |
| 通知 `body` | 通用“日历已更新，请同步闹钟” | 不解析、不计算时间、不执行链接 |
| 目标日历 | 快捷指令中手工选择的一个 iCloud 日历对象 | 不从通知输入替换，不搜索全部日历 |
| 事件标题 | 手机日历的“标题”属性 | 仅判断开头是否为 `[闹钟]`，不从标题抽取“几点” |
| `StartDate` | 手机日历事件的“开始日期”属性，含日期和时间 | 是事件时间来源；不使用结束日期 |
| `LeadMinutes` | 快捷指令顶部固定“数字”动作，默认 `15`，可手工改为 `0` | **不是**通知正文、日历备注或日历“提醒/Alert”字段 |
| `Target` | `StartDate − LeadMinutes`，归一化到分钟起点 | 按完整日期校验窗口，再用于 Clock 钟点 |
| 事件“提醒/Alert”、备注、URL | 原日历可能有这些字段 | 本版不读取来决定 Clock；保留原日历提醒 |
| 受管标签 | 本机由 `Target` 生成 `CALSYNC\|v1\|yyyy-MM-dd HH:mm` | 分钟级去重及隔离个人闹钟，不是事件稳定 ID |
| `request_id` | 云端逻辑变更批次的唯一请求 ID | 保护发送尝试；不假定手机能从通知读到它 |

**算例：**一个已同步到手机的事件，开始日期为明天 09:00，`LeadMinutes=15`，目标为明天 08:45；若该目标距离当前超过 23 小时，此轮不创建，等下一次进入窗口再建。日历原有“提前 30 分钟提醒”仍属于日历通知，不会把 Clock 的 15 分钟自动改为 30，也不会与 `LeadMinutes` 再叠加一次。

以后若要每个日程不同提前量，应另行规定一个受控字段、数值范围、缺省与冲突规则，并在手机上验证可读取性；第一版没有实现该解析，不能先往备注里写 `提前10分钟` 就声称已支持。

### 版本门槛

- **iOS 27：**Apple 的固定版本手册列出 Notification 触发器，可指定 App，并按 Title、Subtitle、Message 筛选。先检查实际手机有此入口且能选择 Bark，再走通知路线。[Apple iOS 27 事件触发器](https://support.apple.com/guide/shortcuts/event-triggers-apd932ff833f/10.0/ios/27)
- **iOS 26 及未出现该入口的设备：**不要照抄新版本界面。iOS 26 固定版手册没有通用通知触发器；使用手动入口或定时自动化，见第 7 节。[Apple iOS 26 事件触发器](https://support.apple.com/zh-cn/guide/shortcuts/apd932ff833f/9.0/ios/26)
- **有通知触发器不等于已证明锁屏全自动。** Apple 的 iOS 27 免询问名单未明确列入 Notification；Bark 是否可选、字段匹配、每次是否需确认及锁屏执行，都要在目标 iPhone 验收。[Apple 自动化与锁屏设置](https://support.apple.com/guide/shortcuts/add-automations-apdfbdbd7123/10.0/ios/27)

先到“设置 → 通用 → 关于本机”查看版本。本文不要求为了测试升级系统，也不推断任何特定手机已经支持。

### 四种结果要分开记录

1. **服务接受：**`bark_send` 返回 `accepted`。
2. **手机收到：**设备所有者实际看到该条通知。
3. **快捷指令执行：**手机显示该次执行的结果，日历已在手机可读。
4. **闹钟可用：**“时钟”出现正确时间、启用状态和声音，并通过实际响铃测试。

前一项不能证明后一项。模块离线测试不验证这条手机链路；本方案的 Clock 创建、取消、重复通知和锁屏场景尚待 iPhone 验收。任何已通过的单次通知收讫，也不能外推为未来通知必达。

## 2. 现有模块怎样发“同步信号”

以下是 `bark_send` 的**示意参数**，不是已发送的请求：

```json
{
  "request_id": "calsync.example-batch-001",
  "title": "CALSYNC-NOTICE",
  "body": "日历已更新，请同步闹钟。",
  "group": "calendar-alarm"
}
```

- `request_id` 由宿主为一个逻辑变更批次生成一次；同一批次沿用它。示例 ID 不可原样用于所有真实通知。服务器 guard 的重启/多实例限制仍适用，见 [guard 协议](GUARD_CONTRACT.md)。
- 一批增删改合并一条信号；普通完成通知使用其他标题，避免每次任务完成都触发建闹钟。
- `title` 用于手机过滤。`group` 只用于通知分组，不是已验证的快捷指令过滤字段，也不是幂等键。
- 本模块只接受 `request_id`、`body`、可选 `title`、`group`、`url`。**不支持 `ttl`、`subtitle`、`expires_at`、`sound`、`call` 或任意额外字段**，不能照搬 Bark 上游参数后假定可用。以 [参数验证源码](../src/validation.js) 为准。
- 不传 `url`。模块的点击链接仅支持白名单 HTTP(S)，不能填 `shortcuts://`；新增 URL scheme 支持需要另行设计和代码审查。
- 仍是普通 `active` 通知，不升级 critical/timeSensitive，不循环响铃，不突破专注模式。
- 标题、正文、分组均经过 Bark 服务和 Apple APNs。只发通用信号，不携带日历标题、人员、地点、账户地址或凭据。
- 发送同步信号须有对应内容、目的和频率的许可。研究或安装这个方案，不代表已经授权未来每次日历变更都发通知。

云端顺序固定为“日历操作成功 → 回读成功 → 发信号”。写入失败不发成功信号。`unknown`、超时或断线时遵守模块的 `automatic_retry: false`，不换 ID 盲目重发；手机本地重查日历与云端重发推送是两回事。

## 3. 手机首次准备

1. 打开 iPhone“日历”，确认目标 iCloud 日历可见，且云端测试事件已出现在手机上。若未出现，到“日历 → 日历列表”下拉刷新；不要把云端回读成功当作手机已同步。[Apple 日历同步排查](https://support.apple.com/en-lb/102543)
2. 选定**一个**自己管理的私人 iCloud 日历，建议命名“闹钟日程”。快捷指令中直接选这个日历对象，不使用“所有日历”；不从通知选择日历或账户。
3. 仅为标题以 `[闹钟]` 开头的非全天事件建闹钟，例如 `[闹钟] 出门准备`。排除生日、订阅日历、全天事项；若使用邀请，排除已拒绝项，所需字段不可用时先不纳入邀请。
4. 第一版统一提前 `15` 分钟；如需开始时响改为 `0`。先不要支持正文自定义提前量或自然语言解析。
5. 保留原日历提醒和重要事项的人工备用闹钟。普通 Clock 闹钟不能当作有保证的医疗、安全或紧急告警。
6. 在“快捷指令”新建“同步日历闹钟”。先按第 4 节搭成预览版，再在解锁状态首次运行，按手机提示完成日历读取、闹钟操作等授权。未经首次授权直接锁屏测试可能停在询问界面。

## 4. “同步日历闹钟”的具体动作

Apple 提供 Find Calendar Events 与过滤动作；iOS 17 起 Find Alarm 可按条件查找。动作中文名称和可见参数可能随版本变化，下面给出英文关键词便于搜索。[查找与过滤动作](https://support.apple.com/guide/shortcuts/intro-to-find-and-filter-actions-apd3c845e881/10.0/ios/27)、[Find Alarm 更新说明](https://support.apple.com/en-mk/111098)

### 4.1 在顶部固定这些配置

用“数字”“文本”“设定变量”等动作保存：

| 配置 | 建议值 | 用途 |
|---|---|---|
| 目标日历 | 手工选定“闹钟日程” | 固定可信数据范围 |
| 标题前缀 | `[闹钟]` | 明确哪些事件需要闹钟 |
| 提前分钟 | `15` | 事件开始前多久响 |
| 窗口小时 | `23` | 只处理即将发生的时刻 |
| 最少余量秒 | `60` | 避免创建时已跨过目标分钟 |
| 管理标签前缀 | `CALSYNC\|v1\|` | 与个人闹钟隔离 |
| 预览模式 | 初次 `开` | 只显示计划，不改 Clock |

标签前缀是实际文本 `CALSYNC|v1|`，表格中的转义符不属于内容。不要把普通个人闹钟改成这个前缀。若安装多份方案，每份使用不同的固定前缀，且各自只管理自己的标签。

### 4.2 先完整计算目标清单，不边读边删除

1. **当前日期 / Current Date**：保存为 `Now`。
2. **调整日期 / Adjust Date**：`Now + 23 小时` 保存为 `WindowEnd`；再加提前分钟，得到 `QueryEnd`。
3. **查找日历日程 / Find Calendar Events**：日历等于所选日历，开始日期在 `Now` 与 `QueryEnd` 之间，按开始日期从早到晚排序，关闭结果数量限制。前缀/全天等条件若不能直接筛选，在下一步用“如果”判断。不要将上一动作的日期列表误作为此动作的数据源。
4. **重复每一项 / Repeat with Each**：标题必须以 `[闹钟]` 开头，非全天，未被拒绝；取完整开始日期，减提前分钟得到 `Target`。先将秒和小数秒归零到该分钟起点，再做下面的比较；预览时确认日期转换没有丢失年月日或误读时区。后续创建/打开前都检查同一个归一化后的 `Target`，不要拿未归零的秒数通过检查、却写入更早的钟点。
5. 目标清单保留 `Now < Target < WindowEnd` 的条目，再单独标记是否满足 `Target ≥ Now + 60 秒` 的写入余量。不足 60 秒时不新建或重新打开，但已存在的正确启用闹钟必须保留；不能因为不允许新建就把它当成已取消。时间已到的条目不再新建，结果标注“需要手动核对”，不要将过去的 HH:mm 写成明天同一时刻。
6. 用 **格式化日期 / Format Date** 将 `Target` 格式化为 `yyyy-MM-dd HH:mm`（24 小时制，设备当前时区）。生成标签，例如 `CALSYNC|v1|2030-05-02 08:45`。示例日期仅演示格式。
7. 以完整标签为键保存 `{标签, Target}`。使用“词典/设定词典值”，或用“列表 + 如果未包含则添加”去重。**同一分钟多个事件合并为一个闹钟**，本版不在标签暴露事件标题；更名不改变响铃时间时不会多建一个。
8. 得到完整 `Desired` 清单后才进入写入阶段。读取失败、超时、权限提示或结果异常时停止，保留现有闹钟，不把错误转换成空列表。

第一轮保持预览模式：用“显示结果”列出日期、钟点、将新增/保留的数量，确认正确后才关闭预览。自动化正式使用时移除这类需要点击的阻塞动作，改用末尾“显示通知”。

### 4.3 新增、复用和去重

对 `Desired` 中每个目标：

1. 写入前再次取当前日期，检查至少仍有 60 秒余量。不足时只核对、保留已有正确启用项，不新增/重新打开，标注“临近或已过时间，需核对”。运行变慢时不把过期钟点留给次日。
2. **查找闹钟 / Find Alarm**：标签/名称**精确等于**目标标签，不用“包含 08:45”这样的宽泛条件。
3. 没有匹配时，**创建闹钟 / Create Alarm**：时间用 `Target` 的本地 HH:mm；标签使用完整目标标签；重复设为“永不”。若动作界面未暴露重复参数，创建后在时钟验证确为非重复。
4. 只有一个匹配时，先核对实际钟点、标签与非重复属性均正确，再用 **切换闹钟 / Toggle Alarm** 的明确“打开”模式。不能用“翻转”，否则重复运行会把正确闹钟关掉。若同标签有多个，第一版不自行选“第一项”关掉其余项，而是保持现状、报告重复，待用户确认后手动清理；原因见第 6 节。
5. 若有人手动改了受管闹钟的钟点/重复规则，不仅凭标签认为正确：停止并提示修复，或在明确选定的修复流程里新建正确项并关闭错误项。若快捷指令无法读取核验所需属性，也停止该标签的修改并提示用户检查，不能猜测。约定不在 Clock 手改受管项目，改日历后重新同步。
6. 结尾重新查找本轮 `Desired` 的标签，只读核对数量、钟点、非重复及启用状态；报告重复或缺失，不在这一轮自动关闭重复项。临近、已过时或不在 `Desired` 的标签，不在此步骤启用或关闭。未来只有实现了真实串行机制，且操作当下仍有至少 60 秒余量，才可增加自动清理重复项。
7. 末尾 **显示通知 / Show Notification**：只报告“按本机日历完成：新增 N、保留 N、待核对 N”。不要写“云端全部同步完成”，也不要让此通知使用 Bark 信号标题。

不调用 Delete Alarms；第一版重复项只报告，用户手动清理。停用和重新打开的行为、默认铃声与稍后提醒，仍要在这部手机上实测。仅在 Clock 手动关闭一个未来受管闹钟，可能被下一次同步重新打开；要跳过该次提醒，应在受控日历中修改该次事件/标记，或停用本方案后处理。

### 4.4 取消与改期：默认报告，可靠自动关闭需扩展

只处理前缀**严格等于本方案前缀**且能解析出合法完整日期的标签。格式异常、前缀近似或普通个人闹钟一律不碰。

- **改期后新时刻进入窗口：**先建好并验证新标签，再处理旧标签；若创建新项失败，不批量关掉现有项目。
- **改期到窗口之外：**此刻不建远期普通闹钟；旧标签只有在确认本机日历已更新后才关闭，后续定时/手动同步再建立新时刻。
- **取消：**只有下一次有效同步或人工处理才能关闭旧闹钟。推送服务不能远程撤回 Clock 闹钟。
- **初始设置阶段：**对“旧标签不在 Desired”的项目只报告候选关闭项，不自动关闭；先完成取消/改期验收。
- **启用自动关闭前：**除取消/改期验收外，还须实现并验证不会交叉应用旧快照的串行机制，再短间隔重查并比较目标清单（第 6 节）。一致、读取成功且无异常时，才可按用户选择关闭未来的旧受管标签；纯快捷指令第一版默认仍是报告候选、人工确认清理。这仍以手机缓存为准，不能证明云端最新状态。
- **意外空清单：**只要曾有未来受管闹钟而本轮突然全空，默认保留并报告“待核对”。用户在日历确认全部取消后，手动运行一个带确认的清理分支；不要因一次空结果批量关闭。
- **已过时间的受管项目：**不重新打开。不要在可能正在响铃或稍后提醒期间自动关闭；基础版留给用户手动清理。旧标签留在 Clock 不影响按完整日期去重。
- **即将响铃的受管项目：**目标在当前后 60 秒内时，不因本轮新建余量不足而关闭。若确实临时取消，提示用户直接到 Clock 核对处理。

这一默认选择会优先避免误关重要闹钟，但同步延迟时可能保留一个已经取消的旧闹钟。需要“取消后立即可证实地不再响”，应实现第 9 节的版本化确认流程，或直接在手机核对并关闭，不能靠多等几秒承诺。

### 4.5 为什么只用 23 小时

普通 Clock 闹钟是钟点和可选星期重复，标签写日期不使它具备任意未来日期预约语义。[Apple 设置闹钟](https://support.apple.com/en-us/118444)

因此绝不能现在为一周后的 09:00 直接创建普通 09:00 闹钟。23 小时窗口是本设计留余量的保守规则：在时区和时钟不变的普通日期，窗口内的下一次该钟点才与目标对应。晚上同步能覆盖次日清晨；更远的事件等以后进入窗口再创建。

跨午夜按完整日期减提前量。例如 00:10 开始、提前 15 分钟，目标为前一天 23:55；查询上限必须加提前量，不能只筛“今天”，也不能只处理日历日期字符串。

旅行换时区、手动改时钟、夏令时跳变会破坏这个简化前提。第一版不保证这些场景；变更前后手动复核受管闹钟，必要时停用自动写入。不要把“少于 24 小时”当作所有时区下的严格保证。

## 5. 把 Bark 通知接到这个快捷指令

### 5.1 先只验证触发，不立刻改闹钟

1. 新建临时快捷指令“Bark 触发检查”，只放“当前日期 → 格式化日期 → 显示通知”，内容为“触发检查完成 + 本机时间”。
2. 若该机采用在快捷指令内添加自动化的界面，打开快捷指令 → 编辑 → 自动化 → 选触发器；独立自动化界面则走“自动化 → 新建个人自动化”。选择 **通知 / Notification**，App 选 **Bark**。以本机实际入口为准；没有 Notification 或不能选 Bark 就停止这条路线。[Apple 添加自动化](https://support.apple.com/en-us/guide/shortcuts/apdfbdbd7123/10.0/ios/27)
3. 添加标题筛选 `CALSYNC-PROBE`。若界面有“等于”优先用等于；若只有“包含”，只用此专用完整标记，并确保普通通知不含它。不要凭分组筛选。
4. 若界面提供“立即运行”，选它；如出现“运行前询问”则按系统允许的设置处理。编辑 → 信息 → 隐私中的“允许锁定时运行”可按需开启，但不承诺它消除全部动作限制。
5. 由已获授权的发送端发**一条**标题为 `CALSYNC-PROBE` 的低敏信号。分别观察 Bark 原通知与快捷指令产生的检查通知；只看到 Bark 不能判定自动化执行。
6. 解锁测试通过，再授权一次锁屏测试；必要时再测专注模式、通知摘要、低电量模式。若仍需点“运行”或解锁，记录为半自动，转第 7 节，不把它写成无人值守成功。

通知预览是否隐藏会影响哪些过滤字段、通知摘要或专注模式会怎样影响触发，都以实际结果为准。不要为测试擅自改用户的全局隐私和免打扰偏好。

### 5.2 换成正式同步

1. 完成第 4 节的手动预览、一次建闹钟及重复运行测试。
2. 停用或移除临时触发检查。
3. 给“同步日历闹钟”添加通知触发：App = Bark；Title 匹配 `CALSYNC-NOTICE`。若本机采用独立自动化编辑器，则在动作里放“运行快捷指令 → 同步日历闹钟”。
4. 自动化不从输入里取脚本名、URL、日历、提前量或 Clock 时间。它始终运行固定同步逻辑。
5. 先在手机确认一个开始于“现在 + 20 分钟”的 `[闹钟] 测试`事件，默认提前 15 分钟，预期约 5 分钟后响。发送一次获授权的同步信号，查 Clock 的时间和标签。
6. 测试完成后关闭/清理对应测试闹钟与测试事件；不要顺手删除个人闹钟。

无需让 Bark “自动点开”一个快捷指令链接。真正的入口是系统通知触发器。`shortcuts://run-shortcut?...` 是在设备上打开后运行的 URL，并不让云端直接调用手机 Clock；本文未给出未制作的分享链接。[Apple Shortcuts URL 说明](https://support.apple.com/guide/shortcuts/run-a-shortcut-from-a-url-apd624386f42/ios)

## 6. 处理延迟、重复和过期

### 日历与推送是两条独立同步链路

可能先收到 Bark，后看到日历更新。重新执行 Find Calendar Events 不等于强制 iCloud 刷新。建议第一轮读取后，短等约 5 秒再读；若清单仍变化，再等约 15 秒读一次。完成后以最后一次成功结果为准，保持流程短小。

这些时间是待验收的设计参数，不是 iOS 后台时限保证。等待期间被中断就未完成，不能报告成功。连续两次清单相同也可能是同一个旧缓存；基础版的结果只能表示“已按本机可见日历处理”。

对临近事件、取消或改期，若本机仍看不到预期变化，显示“待日历同步，请打开日历核对”，保留现有闹钟与定时/手动入口。不要把失败替换为空清单，更不要等几分钟乃至几小时的 Wait 循环占用快捷指令。

### 两层去重不混用

- **云端：**同一变更批次使用同一 `request_id`；持久 guard 才可跨进程保护发送尝试，仍非手机 exactly-once。
- **手机：**同一目标分钟对应同一完整日期标签；先查再建，最后只读查重。顺序重复运行应复用同一闹钟，而不是每次新建。
- **并发例外：**两次自动化若同时“查不到”后创建，仍可能出现重复；若各自保留不同“第一项”并关闭其他项，还可能把两个实例全部关掉。因此第一版检测多项就报告，**不自动关闭重复项**。纯快捷指令的普通文件读写不能当作原子锁。
- 第一版限制入口数量、云端合并批次，专门测试快速重复触发；一旦出现重复或交叉执行，暂停无人值守并手动清理，再使用已隔离的手动/定时入口或开发真实串行接收端。一次测试通过不是系统永不并发的证明。自动取消、替换及重复清理的可靠版本还需要第 9 节的串行/版本机制。

### 没有 `ttl`，怎样避免旧信号设错闹钟

本模块没有推送过期字段，不能保证旧通知不晚到。基础版不读取旧通知中的钟点，只重新计算**现在**起 23 小时内的手机日历，所以旧信号至多造成一次额外同步；它不会有意重放一条旧建闹钟命令。

这不解决“手机日历仍是旧内容”的问题。若将来添加关联 ID、发送时间或版本号，可放在现有低敏正文中，但必须先确认本机能读取通知输入，再在固定格式与长度范围内解析；不能假定过滤条件自动等于可读取的结构化输入。第 9 节列出更可靠的扩展要求。

### 如果需求是“收到通知后立即响闹钟”

可单独设计“Bark 提醒转闹钟”：将目标设为当前分钟起点再加 2 分钟，留出约 1–2 分钟执行余量。它与“按日历时间响”是两种用途。

第一版**不默认启用**该模式：旧通知晚到也会产生新响铃，同一通知重复到达可能多次响。必须先具备可验证的信号 ID、发送/过期时间、消费记录与最大延迟限制，再通过实机测试。不能用“当前分钟”或把 `Now + 1 分钟` 简单截断后直接建闹钟，也不能宣称收到信号就能精准立刻响。

## 7. 没有通知触发器时的兜底

### 手动入口，优先保留

把“同步日历闹钟”加到主屏幕/小组件或控制中心；需要时点击或让 Siri 运行。云端完成后，用户在手机运行它，核对 Clock 结果。这条路线不依赖 Bark 直接打开链接，也不要求模块放开自定义 URL scheme。

### 定时补偿

建立两个“特定时间”自动化，例如每天 06:00、21:00，均运行同一个快捷指令；如界面允许，设置“立即运行”或关闭“运行前询问”。定时触发在 Apple 的可自动运行名单中，但各动作首次授权仍需完成。[Apple iOS 26 自动运行设置](https://support.apple.com/zh-cn/guide/shortcuts/apd602971e63/9.0/ios/26)

两次运行的最长正常间隔可达 15 小时，不能保证午后临时新增的近时事件。此类事件须手动同步或保留独立闹钟。定时是补偿手段，不能把“每天检查两次”写成实时联动。

App 打开/关闭、充电、NFC 等可作为额外手动行为触发，仍不等于云端写入立刻执行。不要为追求实时设置长期 Wait 循环。特定时间的重复是每天/每周/每月，不是一个内置“每隔几分钟永久执行”的开关。

## 9. 后续可扩展设计，尚未实现

### V1：不改服务器代码，先完成手机规则

本方案主体：固定标记唤醒、指定日历、23 小时窗口、分钟合并、专用标签、保守清理、定时兜底。当前仓库只提供通知模块和这份搭建文档，不附带安装好的自动化。

### V2：有版本的同步请求与回执

若需要知道“这次云端改期已经体现在手机闹钟”，增加一个独立、私有、需鉴权的协调协议，不能仅靠 `accepted`：

1. 云端把每次已提交日历变更记录为不透明 `batch_id`、版本、允许的事件关联标识和失效时间；标识不得编码账号、标题或人员信息。
2. 手机先拿到并验证预期版本，再检查本机指定日历是否已呈现对应变更。新增、改期、取消都需要可判别的证据；尤其取消不能只凭找不到一条缓存记录就认定已同步。
3. 幂等地应用闹钟差异，手机读回 Clock 核对，再回报“本次版本已应用/待同步/失败”，只含低敏版本号和计数。
4. 服务端保留有限期状态，用它解释当前结果。回执中断不等于未执行，不盲目重试建闹钟；先让手机按目标状态再次核对。

设备鉴权、持久授权、回执数据发送、隐私/存储期限和串行处理都需要单独审查。不要把服务端设备 key、日历密码或可公开调用的闹钟控制 API 塞进快捷指令、推送或公开仓库。该层目前没有实现，也没有新增 MCP 工具或线上地址。

### V3：稳定事件身份与更复杂的提醒规则

- 如本机确实能读到稳定事件 ID，按“日历 + ID + 重复事件发生实例”关联；否则使用本机受控映射，并诚实说明改期会表现为旧标签退出、新标签进入。
- 支持不同事件提前量、多次提醒、时区/DST 变更、用户对单次提醒的忽略；先定义规则冲突和误触风险，再扩充配置。
- 若必须按任意未来日期可靠排程，评估专用 iOS App 的系统闹钟能力。它不是“云端直写 Apple Clock”的现成接口，需单独开发、权限和设备验收。

## 10. 停用与排错

- **只收到 Bark：**检查系统版本、Bark 是否可选、标题过滤实际匹配、自动化是否启用、是否等待确认/解锁。不要反复发推送代替诊断。
- **快捷指令执行但没闹钟：**先看手机日历是否真的出现事件、日历对象是否选对、`[闹钟]` 前缀/全天条件、提前量、23 小时窗口和 60 秒余量。
- **时间不对：**核对 24 小时制、完整日期减提前量、重复为“永不”、设备时区和人工改钟；暂停自动写入后修复。
- **停用：**先停用通知/定时自动化，再按完整专用前缀检查并手动关闭未来受管闹钟。只关闭服务器 Bark 开关不会撤销 Clock 中已经建立的闹钟。
- **恢复：**先手动预览和同步，确认列表，再启用自动化；不需要重置或公开设备 key。
